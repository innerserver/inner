# Connectifi v263: dynamic PTMs, teacher requests and student parent contacts

25 November 2026.

## PTM tab lifecycle

Parent teacher meetings now has its own app view and navigation entry. It appears when the signed-in account has a relevant, upcoming, uncancelled teacher schedule or an unexpired pending/accepted meeting request. A dashboard shortcut appears with it. The tab disappears when no active content remains, and an empty active PTM view returns to Dashboard. Students only see eligible grade schedules and their own requests; teachers see their schedules/requests; admins retain management visibility. Scheduled refreshes check expiration, and existing school update notifications trigger refreshes. Logout clears PTM request/schedule UI and navigation state to prevent stale content appearing for another account.

Existing admin schedule creation remains available in dashboard school actions even when there are no active PTMs. The existing slot duration, break, date, booking and conflict protections are retained.

## Teacher requests

Teachers can use Request PTM with student in the school actions. Recipient choices are student accounts reachable through the teacher's room access; admins can select any student. Requests include a teaching subject, message, an optional active schedule owned by that teacher for the student's grade, and an optional expiration. The default lifetime is 14 days, with a maximum of 90 days. Duplicate active requests for the same teacher/student/schedule are blocked, and the store is bounded to 2,000 requests.

Only the addressed student can accept or decline. The sender or an admin can withdraw a request. Acceptance acknowledges the request without reserving a slot; a linked schedule still requires a separate booking. Booking a linked slot marks the corresponding active request booked. Standalone accepted requests remain visible until withdrawn or expired so the parties can arrange a meeting. Requests are in-app; this release does not automatically send emails to parents.

## Student-only registration and parent emails

New student accounts require one to three valid, distinct parent emails. The first UI field is mandatory and the other two are optional. Addresses are trimmed/lowercased and validated independently of student-email domain restrictions. Public signup and public account requests reject teacher, moderator, admin, developer, HMD and parent role submissions at the server, including manipulated role/requestedRole payloads. Public grade choices exclude Staff and Other. Public request approval creates a student; staff accounts use the existing admin creation flow instead. Approval of a legacy request without parent contacts prompts the admin to supply them.

The student profile includes the parent-contact fields, and admin student creation includes them. Saving a student profile cannot clear the last parent email. Existing students are not deleted or assigned fabricated contacts: students lacking these details must add at least one when they next save their profile. This release does not lock all legacy accounts out of existing features until they do so. Parent addresses do not create parent accounts, confer login/reset rights or become automatic mail recipients. They are not verified by OTP in this release.

Addresses are stored on the user record, restored from authoritative account data in /api/state, and exposed through safeUser only to the account itself and authorized admins. Other students/teachers do not receive another student's parent contacts merely through PTM access. Admin account cards can show the contacts when the server includes them. Existing privacy controls and account passwords are unchanged.

## Routing and UI

The PTM request buttons wrap on phone screens, and parent-contact fields use a bounded, spaced group. Existing wallpaper and sticky profile save behavior remain. The server now serves the app shell for its explicit known route list, including /ptm and /profile, so reloading these views works. Unknown paths still return real 404 responses and API authorization remains unchanged. The only navigation addition is the conditional PTM entry; existing sidebar geometry is retained.

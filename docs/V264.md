# Connectifi v264: reliability guardrails and owner-controlled secret access

25 November 2026.

## Implemented

The common HTTP/HTTPS server factory now applies the existing timeout/header/request-per-socket defaults consistently, including isolated local/test servers. Defaults are 15-second header timeout, 120-second request timeout, 5-second keep-alive timeout, 100 requests headers and 1,000 requests per socket. Plain HTTP explicitly uses a 16 KB maximum header size. New defaults bound active HTTP requests at 1,024 and TCP connections at 2,048. Set INNER_MAX_ACTIVE_HTTP_REQUESTS and INNER_MAX_HTTP_CONNECTIONS to tune these bounded values. Excess admitted work receives a generic 503 with Retry-After: 2; completion or disconnect releases its slot exactly once. Existing WebSocket client/queue/frame/origin/authentication limits remain in use.

These are admission/resource controls. They do not guarantee resistance to distributed traffic, saturating network links or every form of packet manipulation. Render documents platform DDoS protection, but account settings, origin exposure, real traffic and downstream services still need an operational review. Reference: https://render.com/docs/ddos-protection

Owner-admin secret-conversation access is retained, as the user confirmed. Other users remain governed by the existing owner-managed allowlist. Secret shared-message visibility no longer retains a sender exception after removal from the list. Secret DMs require both current allowlist membership and participation, except for owner admins. Secret DM attachment-context access and live delivery also check current permissions. This cannot erase messages or files already received or downloaded by a previously authorized user, and it is not end-to-end encryption or protection against infrastructure/database administrators.

Teachers/moderators already have ordinary-room access under canAccessRoom. No covert DM monitoring or hidden-presence mechanism was added. Ordinary DM access rules remain unchanged. Any expansion of moderation access needs a clearly disclosed, logged workflow. No usernames were newly granted secret access.

## Normal failure and call checks

124 existing/added automated checks pass, including request-limit recovery after finish/disconnect, owner secret access, allowlist removal, connection-state rendering and existing authorization/body/upload failure cases. These are regression and feature checks, not a completed broad security audit.

Two isolated local browser contexts used synthetic cameras/microphones and fixture accounts. An initial unfocused run did not establish both streams. With foreground handling, a call connected and the receiving peer recorded 85 audio packets / 4,228 audio bytes. Video reception was not verified; a later repeat also encountered a media-startup timeout. No calling-code change is being described as a video fix. Cross-network TURN calls, real microphones/cameras, mobile calls and screen sharing were not verified. No real browser profile or account was used.

## Security-audit handoff and secrets limitation

The separate audit chat was explicitly blocked by the platform cybersecurity filter. At the user's request, a materially narrower, read-only configuration/hygiene prompt was sent, excluding traffic generation, attack reproduction and safeguards bypass. That narrower turn was blocked too. No repeated rewording or transfer of the blocked audit to this chat was performed. The platform message points to https://platform.openai.com/settings/organization/status-and-access for Daybreak access. The broad audit and an exhaustive repository/history/browser secret-exposure review remain incomplete, so this release does not certify that the repository or deployment is secret-free.

Browser-called API endpoints and delivered front-end code are inherently inspectable. WebRTC also requires client TURN credentials: a static relay password given to the browser is inspectable. Long-lived relay master secrets should stay on the server, with short-lived provider/coturn credentials sent to clients. The live TURN setup was not changed or tested, avoiding an unverified configuration switch. No hosting settings or real credentials were changed. Coturn reference: https://github.com/coturn/coturn/blob/master/README.turnserver
